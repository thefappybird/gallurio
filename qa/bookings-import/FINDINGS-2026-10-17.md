## Plan implementation check

Both `docs/bookings/import-and-document-themes.md` and `docs/bookings/import-qa-fixes-plan.md` have corresponding code and focused tests in this branch. I checked the mapping and date normalization, CSV/XLSX intake and limits, review and result UI, sheet resizing, global 404, invoice theme resolution, and full-screen document preview. The focused suite passed **290 tests across 16 files**. Browser checks confirmed the key file handling, theme dialog, preview expansion, and 404 behavior. The published seed workspace had a portfolio, so the unpublished portfolio fallback was covered by unit tests only.

The original README issues fixed in this QA pass were: a vague missing-client reason, mobile review clipping, the generic `.xls` error, raw server result codes and nonlocalized completed-booking text, and slow serial commits. The QA cleanup script now recognizes the four encoding-fixture client names while refusing clients linked to non-QA bookings. Full `pnpm typecheck` and `pnpm lint` pass; lint still reports 246 warnings and zero errors. The first typecheck hit a stale generated Next route reference; `pnpm exec next typegen` refreshed it.

## Follow-up status (2026-10-17)

- **Overnight rows — resolved by product decision.** Keep the shared same-day booking rule. The QA guide now expects the 22:00 to 02:00 row to skip, and the durable import documentation names this validation rule.
- **Offline commit feedback — fixed.** A rejected commit fetch now warns that the result is unknown and asks the owner to check the booking list before retrying. This is more precise than calling the import failed, since a server can finish after a response is lost. All five locale catalogs and a focused UI test cover it.
- **500-row duration — background job implemented; deployed timing remains open.** The importer no longer re-reads clients it just created in the same transaction. The synchronous path improved from 93.8 to 82.5 seconds in development. The new background path returned a job ID in **3.7 seconds** and finished 500 rows in **99.7 seconds** in Chromium, with zero row errors, import API 5xx responses, or uncaught page errors. The panel showed progress, survived close/reopen, and refreshed bookings on completion. The additional job-outcome write makes total processing slower than the optimized synchronous path, but the owner is no longer held in one long request.
- **Verification and cleanup.** The final focused import, transaction, and locale suite passed **155 tests across five files**. `pnpm typecheck` passed. `pnpm lint --quiet` passed; the preceding full lint run reported 246 existing warnings and zero errors. Playwright confirmed CSV, XLSX, multi-session, mixed-error, and 500-row background imports. The final run created 511 QA bookings and 509 job items across four jobs; the reviewed cleanup removed all of them. A final dry run found zero QA bookings, clients, transactions, activity logs, jobs, or job items.

## Background import release check

The branch now has a MongoDB job and one outcome record per booking group, with a unique workspace/request ID and one-active-job index. Booking writes and successful group outcomes commit together; the status endpoint reports progress and can reclaim an expired job. A lost start response is looked up by request ID, and the same ID is reused on retry. The UI distinguishes an already-running import from the newly submitted file.

The browser run was local development against Atlas. **Release gates still open:** repeat the 500-row check behind the actual Caddy/Cloudflare deployment, and verify that a job resumes after the app process is restarted mid-import. The current worker resumes when a status request reaches an expired lease; it does not scan for orphaned work at startup. A job can therefore remain pending until the owner reopens Import. The progress endpoint took roughly one second per request against this development database, so watch polling load in the deployed run. New job and item indexes need rollout review; no reindex script was run.
